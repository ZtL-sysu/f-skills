# F Research V1

## Theory-only requests

When the user explicitly requests a theoretical article without experiments, first load [references/theory-only-mode.md](references/theory-only-mode.md). Its authorized, separately recorded profile maps the existing stage IDs to proof-based gates and permits the actual native writing executor; empirical defaults below do not manufacture experiment obligations for this mode. Preserve empirical contracts unchanged.

## Execution contract

Read [references/execution-contract.md](references/execution-contract.md) at startup, resume, and correction, and [references/research-recovery.md](references/research-recovery.md) before P0 and every experiment repair. Initialize `pipeline-state.json` from `assets/pipeline-definition.json` using `scripts/pipeline_state.py --init` with the state path as its positional argument. Maintain the Markdown ledger as its readable view. Validate `--before <stage-id>` before starting a stage and `--complete` before delivery. The JSON definition is the canonical stage list; the workflow below defines the substantive gates. Record current user preferences and authorized scope once in a versioned run-local contract. This skill does not change the selected model or global settings.

## Overview

This is a strict end-to-end workflow for turning a user-provided guidance Markdown file into a complete first-draft paper. Treat the guidance file as the contract: it must define the paper outline, story, expected contribution, and detailed experiment plan.

All process files and final deliverables must live under the directory that contains the guidance file. At P0, resolve the absolute guidance file path, set `guidance_dir = dirname(guidance_file)`, and create a single run root under it, such as `<guidance_dir>/f-research-v1-run-<YYYYMMDD-HHMMSS>-<slug>/`. Store every protocol, trace, log, result table, figure source, AutoResearchClaw output, TeX source, PDF, audit file, manifest, and delivery bundle inside that run root. External compute directories and tool caches may exist only as transient locations; anything used for claims or delivery must be synchronized into the run root and recorded there.

Default to local experiment execution in a project-specific Conda environment. Probe and use local accelerators: prefer Apple MPS for supported PyTorch operations on Apple Silicon, use local CUDA when available, and record CPU fallbacks. Do not contact or assume any remote server unless the user explicitly requests remote execution, the guidance contract already selects it, or local feasibility fails and the user authorizes an external machine.

The workflow is baseline-first and evidence-first. Do not start by training only the proposed method. Establish simple and strong baselines first, then improve the proposed method against them. Do not downgrade or skip a guidance target merely because the first attempt fails; debug, strengthen, and rerun until every required experiment is complete and the guidance's strong expected result is met. If the strong target appears impossible, enter the authorized correction protocol in `references/research-recovery.md` before writing; request direction only for a material scope or resource change.

The strong-result lock is deliberately retained. Its protection begins before P2: a binding target is admissible only when the guidance includes a mechanism-supported, baseline-calibrated, compute-bounded feasibility contract. This prevents training against a spectacular but theoretically or operationally impossible result while preserving the requirement to meet an approved strong target before paper writing.

## Strict Pipeline

Execute this pipeline in order. Maintain `pipeline-state.md` from `assets/pipeline-state-template.md` inside the guidance-directory run root. Do not start a stage until the previous stage's gate is passed and recorded.

## Sequential Execution Integrity

`pipeline-state.json` is the structural execution authority; `pipeline-state.md` is its readable view. Its canonical order is `P0 -> P1 -> P1A -> P1B -> P2 -> P3 -> P3A -> P4 -> P5 -> P5A -> P6 -> P7 -> P8 -> P9 -> P10 -> P11 -> P12 -> P13 -> P14 -> P15 -> P16 -> P17 -> P18 -> P19 -> P20 -> P21`. Every stage must be recorded as `pending`, `running`, `passed`, `blocked`, or `superseded`; `skipped` is never valid.

Only a recorded `passed` predecessor authorizes the next canonical stage. The autonomous correction loop may only create explicit back-edges to the earliest affected stage; it must record the trigger, evidence, replacement contract, and re-run result before moving forward again. It may not jump from a failed review to drafting, export, or delivery, and a superseded plan never grants credit to a replacement plan. P21 is invalid unless the ledger proves that all required stages for the accepted contract passed in canonical order.

| Stage | Action | Gate to advance |
|---|---|---|
| P0 | Load the user guidance file. If missing, locate an existing user-supplied contract or complete one from the authorized inputs; request only the essential missing research choice if neither is possible. Resolve `guidance_dir`, create the run root under that directory, and initialize `pipeline-state.md` plus a path-containment manifest there. | Guidance file exists; run root is inside `guidance_dir`; `pipeline-state.md` and path-containment manifest exist in the run root. |
| P1 | Validate the guidance file against `references/guidance-file-spec.md` and load its `ccfa-startup-packet/` when it exists. | Story, outline, expected results, datasets, baselines, metrics, experiment schedule, and the startup decision are explicit. A packet marked other than `proceed` blocks the run. |
| P1A | Run the strong-result feasibility lock before any environment setup. Use the packet's `claim-evidence-matrix.md` and `strong-result-feasibility-contract.md`; if absent, create equivalent artifacts with `ccf-experiment-designer` and record why the pre-guidance CCFA path was unavailable. Verify each binding main claim has a mechanism and falsifying ablation, a direct simple/strong/matched baseline path, a metric-calibrated `minimum`/`expected_strong`/`failure` condition, a code or adaptation route, prototype milestone, compute-memory-runtime budget, seed and search budget, and stop-and-return condition. | `strong-result-feasibility-lock.md` is recorded in the run root with every main claim `pass` or `block`. Only all-pass plans enter P2. A block returns to guidance design; it must not be solved by lowering `expected_strong`, inventing a result, or starting proposed-method training before the relevant baseline path is viable. |
| P1B | Run `ccf-idea-reviewer` in standard mode as the pre-experiment adversarial review, using the literature map, mechanism card, claim-evidence matrix, and feasibility contract. Run `ccf-integrity-auditor` in `claim-audit` mode over the same planned claims, explicitly marking every claim as planned evidence rather than reported evidence. Record `ccfa-pre-experiment-review.md`, `ccfa-pre-experiment-integrity.md`, and a concern-to-action ledger in the run root. | No fatal novelty, soundness, feasibility, or claim-support risk remains unresolved. Every score deduction has a repair condition. A `pivot-with-rescue-route`, `needs-literature-search`, unsupported binding claim, or unbounded implementation risk enters the autonomous correction loop; P2 begins only after a repaired or replacement guidance contract passes P1A and P1B again. |
| P2 | Convert the guidance experiment plan into runnable local protocols and commands, select or create the project Conda environment, probe CPU/GPU/MPS support, and execute the first setup/code checks on the local machine. Do not start AutoResearchClaw yet. Use remote setup only when the contract explicitly authorizes it. | Runnable protocols, local environment checks, commands, accelerator decision, and artifact paths exist in the run root; any authorized external paths have a synchronization plan. |
| P3 | Baseline-first execution gate. Run or adapt the simple baseline and the strongest feasible recent/domain baseline before claiming proposed-method progress. If a strongest baseline cannot run, preserve logs, error text, code/checkpoint audit, and a substitute direct baseline rationale; unresolved baseline gaps block strong claims. | Baseline metrics and reproducibility artifacts exist before proposed-method iteration. |
| P3A | Run a baseline-evidence stop-loss review before the full proposed-method campaign. Use `ccf-integrity-auditor` in `numeric-audit` mode to check baseline metrics, units, splits, seeds, and metric direction; then use `ccf-idea-reviewer` in standard mode to reassess whether the observed baseline landscape still supports the mechanism, novelty delta, and binding `expected_strong` target. | `ccfa-baseline-evidence-review.md` and `ccfa-baseline-numeric-audit.md` confirm that the proposed experiment still has a credible differentiating path. If a strong baseline defeats the claimed bottleneck, a baseline cannot be reproduced, or the expected-strong target is no longer evidence-grounded, enter the autonomous correction loop before P4; do not spend the full experiment budget on a contradicted story. |
| P4 | Execute every experiment required by the guidance file: all datasets, baselines, method variants, ablations, metrics, statistical checks, robustness/efficiency checks, and planned result artifacts. Update `experiment-traceability.md` before and after each batch. | Every required guidance experiment is `done` with evidence. `infeasible-with-evidence` rows enter authorized correction and block writing until a valid replacement contract and evidence pass all affected gates. |
| P5 | Strong-result lock before writing. If any result misses the guidance's `expected_strong`, improve and rerun: debug data alignment, strengthen baselines, tune, improve architecture/training/objective, add ablations, or revise implementation. Record every run, failed attempt, metric, config, seed, execution environment, hardware profile, and change rationale. | All required experiments are complete, strong expected results are met for the paper's main claims, and raw data/logs/result tables/analysis notes are sufficient for audit and replots. |
| P5A | Feed accepted scientific facts and material disclosures into the clean packet; keep reviewer wording and administrative verdicts external. Build a concise pre-draft evidence dossier from the approved P5 artifacts: problem/novelty delta, main claims, mechanism and ablations, complete baseline table, seed/statistical evidence, robustness/efficiency evidence, limitations, and planned figures. Run `ccf-paper-reviewer` in `scientific` mode against this dossier, then `ccf-integrity-auditor` in `full` mode against all claim/result/table/figure-source mappings. Record `ccfa-pre-draft-scientific-review.md`, `ccfa-pre-draft-integrity-audit.md`, and `ccfa-pre-draft-action-ledger.md` in the run root. | The independent reviewers find no unresolved fatal soundness, novelty, evidence, reproducibility, numeric-consistency, or claim-support concern. A concern requiring an experiment, correction, narrowed claim, or guidance revision enters the autonomous correction loop; P6 begins only after the repaired evidence package passes P5 and P5A. Paper drafting cannot be used to conceal an evidence gap. |
| P6 | Build a manuscript-facing scientific content packet and brief from accepted P5/P5A evidence using the writing adapter; load the shared scientific-writing contract and academic profile. Keep stage ledgers, lock verdicts, reviewer dialogue, logs, debug chronology, and production notes out of drafting context while retaining evidence links for targeted checks. Run AutoResearchClaw stage 16 `PAPER_OUTLINE` with that packet, the brief, and section tasks. Establish the question/answer, core claim path (Introduction → Methods → Results → Discussion → Conclusion), one-sentence purpose per subsection, scope conditions, terminology, and supporting evidence. Update planned claims from actual results; never treat guidance expectations as findings. | Canonical six-section outline, evidence map, and section-purpose map are consistent with accepted evidence; supporting and auxiliary claims are not forced into repeated full-paper coverage. |
| P7 | Run AutoResearchClaw stage 17 `PAPER_DRAFT` as its own gated stage after verifying the actual context boundary in `references/writing-adapter.md`. Build each writing call through the adapter with the shared contract, approved packet, manuscript brief, and requested section task. Draft in reader-understanding order (Methods/Results may be drafted first internally); organize Results around research questions, report key comparisons and uncertainty without inventorying every table cell, and use figures/tables where they add evidence. After each complete section, make a reverse outline of paragraph contributions; merge adjacent paragraphs with the same job, retain useful prose, and route workflow records outside the manuscript. | Complete evidence-grounded draft with distinct section/paragraph purposes, appropriate visual support, explicit scope conditions, and no administrative process narration. |
| P8 | Select figures and tables from the evidence and manuscript argument. Use `nature-figure` for data plots/tables as appropriate. Preserve Figure 1 as the overall framework/architecture figure and generate it directly with GPT image generation (`image2`) using the style and prompt references. | Each included artifact answers a scientific question, is cited and interpreted near its first discussion, and has an evidence-aligned caption. No fixed artifact count or per-subsection quota applies. |
| P9 | Run AutoResearchClaw stage 18 `PEER_REVIEW` and the required CCFA manuscript review/audit. Convert reviewer concerns into concrete edit actions before revision; preserve reviewer text outside drafting inputs. | At least two AutoResearchClaw reviewer reports, the CCFA full review/integrity audit, and a merged concern-to-action ledger exist; unresolved evidence or integrity concerns are repaired or explicitly blocked. |
| P10 | Translate each reviewer concern into an affected proposition, evidence status and action (`KEEP`, `REWRITE`, `MOVE`, `MERGE`, `NARROW`, `REMOVE_NONSCIENTIFIC`, `BLOCK_EVIDENCE`) with target location and factual check and call Stage 19 through the adapter with only the relevant packet facts, brief, manuscript passages, and actions. Preserve negative and null findings and uncertainty; distinguish observed patterns from plausible explanations. Do not append repetitive disclaimers or weaken valid conditions. | Revision log links concerns to specific actions and passages; factual claims remain supported and appropriate scope conditions are clear. |
| P11 | Run AutoResearchClaw stage 20 `QUALITY_GATE` as a standalone f-research-v1 stage. Check six-section structure, claim/evidence alignment, result strength, figure/table placement, paragraph reverse outline, whole-paper continuity, and distinct Results/Discussion roles. | Quality gate passes without unresolved major issues. |
| P12 | Verify references for authenticity, relevance, claim support, and duplicate versions. Set the bibliography scope from the research question and current venue; do not add citations to satisfy a fixed count or recency quota. | All cited sources are verified and appropriately support their claims; duplicate risks are resolved. |
| P13 | Run AutoResearchClaw stage 22 `EXPORT_PUBLISH` as a standalone f-research-v1 stage. Export TeX source, bibliography, figures, and paper artifacts into the run root. If AutoResearchClaw writes to a default external artifacts directory, copy the accepted export into the run root and treat only the run-root copy as deliverable. | `paper.tex` or equivalent main TeX, bibliography, and figure files exist inside the run root. |
| P14 | Run AutoResearchClaw stage 23 `CITATION_VERIFY` as a standalone f-research-v1 stage. Verify citation relevance, authenticity, placement, and duplicate-paper status against `reference-dedup-audit.md`. | Citation verification passes; unresolved placeholders and duplicate-paper conflicts are fixed or explicitly blocked. |
| P15 | Compile the TeX/PDF with `paper-compile` inside the run root. | The compiled PDF exists in the run root and matches the current TeX/bibliography/figure set. |
| P16 | Apply the current journal/template limits and any explicit author length requirement. With no length target, assess whether the manuscript is complete and proportionate to its evidence; do not expand to a default page threshold. | The current manuscript meets applicable hard limits and contains the material needed to answer its research question without padding. |
| P17 | Re-check the paper against the original guidance file using `paper-guidance-audit.md`. | Every promised experiment, section, claim, figure, table, and analysis is covered; any infeasible item requires versioned correction under `references/research-recovery.md`, with renewed approval only outside the authorized scope. |
| P18 | Audit included figures/tables for evidence, caption accuracy, legibility, textual explanation, and placement. Record omitted artifacts when the omission matters to traceability; do not require a visual for every subsection. | Each included visual has a clear purpose and supports the adjacent scientific discussion; no quota-based visual is required. |
| P19 | Build every subskill call through the writing adapter with the shared scientific-writing contract, academic profile, clean fact packet, and narrowly scoped passages. Resolve installed-first subskills (ml-paper-writing, paper-refine, paper-polish-workflow, humanizer) under this same profile; use bundled copies only when installed copies are absent. Diagnose defects, make justified local edits, then recheck the full-paper narrative. | Changes address named defects; formal academic voice, protected ranges, fact/condition associations, and good existing prose are preserved; the final whole-paper check passes. |
| P20 | Any final rewrite, translation or template conversion uses the same writing contract, rechecks the changed text, and invalidates previous writing acceptance. If a target journal, official author guide, template, special-issue page, or live submission form is available, create `submission-constraints.md` and `manuscript-metadata.md` before final compilation. Record the strictest currently applicable limits and the canonical title, author order, affiliations, corresponding-author order/emails, abstract, keywords, highlights, funding, data/code statement, and required declarations. Hard technical or eligibility limits in the current journal/form cannot be relaxed by a user preference; explicit user choices govern optional content and routing within those limits. Route optional declarations according to the journal/form instead of inserting them into the manuscript by default. Recompile, recount constrained fields, and re-run citation/figure/professionalism checks. | Final TeX/PDF and any title page, cover letter, source archive, or submission fields agree with the canonical metadata; abstract/keyword/highlight limits pass; declaration placement is journal-compliant and non-contradictory; final PDF matches current source. If no target requirements exist, record journal-specific constraints as unresolved in `pipeline-state.md` rather than inventing them. |
| P21 | Deliver final artifacts from the run root. Compare the accepted TeX, compiled PDF text, bibliography, figures, source archive, and package copies after normalization; stale duplicates fail delivery. Extract the final source archive to a clean temporary directory, compile from the extracted contents, and compare that PDF with the accepted output before delivery. | Final delivery includes `.tex`, compiled `.pdf`, figures, bibliography, experiment artifacts, `pipeline-state.md`, traceability matrix, figure/table audit, `reference-dedup-audit.md`, `submission-constraints.md`/`manuscript-metadata.md` when applicable, final audit note, and a manifest proving every local deliverable/process file is under `guidance_dir`; source-PDF-package consistency and clean extraction/compilation checks pass. |

## Autonomous Correction Loop

P1B and P5A must repair or pivot; they must not terminate the automation merely because a CCFA review fails. Create `correction-loop-state.md` and `correction-ledger.md` in the run root at the first failed review. Preserve every review, run, negative result, and superseded plan as evidence.

For each correction cycle:

1. Use `ccf-pipeline-orchestrator` to classify every blocker as `novelty`, `mechanism`, `implementation`, `baseline`, `data`, `compute`, `evidence`, `numeric-integrity`, or `claim-scope`, name the earliest affected stage, and define the next owner and pass condition.
2. Use `ccf-idea-optimizer` to generate concrete repair candidates within the user's original method family and target tier: a narrower bottleneck, a different public-data scenario, a mechanism repair, a defensible method variant, or an evidence route. Do not use it to cosmetically rewrite a failed claim.
3. Use `ccf-literature-searcher` to verify each candidate's novelty delta, direct public dataset access, strong baseline/code path, and current metric protocol. A dataset requiring approval, payment, manual review, or private access is not a valid autonomous repair route.
4. Use `ccf-experiment-designer` to rebuild the claim-evidence matrix, strong-result feasibility contract, and minimum experiment queue from actual available hardware, memory, runtime, seed/search budget, and verified data/code availability. It must reduce cost only when the resulting evidence remains persuasive for the same target tier.
5. Re-run the applicable review gate. Repairs without a contract change reopen the earliest affected stage and its downstream suffix. A versioned contract change reopens from P0 and reaccepts every gate in order, using verified unaffected evidence where valid. P1A/P1B must pass before P2, and P5/P5A must pass before P6.

Read [references/research-recovery.md](references/research-recovery.md) before this loop; its revision and test-isolation rules also govern P1A, P3A, P4, and P5 failures.

At P1B, prioritize a low-cost prototype and direct baseline check before committing the full experiment budget. At P5A, prioritize the smallest missing discriminating experiment, ablation, robustness check, correction, or claim narrowing that resolves the review concern; then expand only when the new evidence shows a credible path to the binding strong result.

The loop may automatically replace the application scenario, claim framing, dataset, baseline plan, evidence plan, or method variant when the replacement stays within the user's original method family, target tier, and real resource envelope. Each replacement creates a new versioned guidance contract and records the prior contract as superseded; the new contract must retain its own binding, baseline-calibrated `expected_strong` target. The loop must never fabricate results, use inaccessible data, assume unowned hardware, erase failed evidence, or quietly lower a target to make a failed direction pass.

If no candidate can pass with directly accessible public data and the verified hardware/runtime envelope, continue screening CCFA-generated alternatives. Request user direction only when progress requires a material change the loop is not authorized to make: a new method family, a different target tier, private/paid/restricted data, additional hardware, credentials, budget, or external collaboration.

## Non-Negotiable Rules

- The guidance file is authoritative unless it conflicts with evidence, feasibility, or research integrity.
- The directory containing the guidance file is the local artifact boundary. All local process files and deliverables must be created under the P0 run root inside that directory. Do not scatter deliverables into global `AutoResearchClaw/artifacts`, `auto-paper`, temp, desktop, downloads, or the current shell directory.
- "Reach the expected result" means improve the method and evidence, not alter reported numbers.
- Do not enter P6 paper writing until P5 passes: every guidance-required experiment is complete and the strong expected result is met for the main claims.
- Claims must be supported by experiments or citations.
- Write scope and limitations as positive evidence boundaries. Prefer "we report sparse activity, SynOps proxies, and local PyTorch latency" over "this is not measured neuromorphic energy"; prefer "learned edges are treated as association patterns" over "this is not causal"; prefer "public-reference rows show the remaining gap to published averages" over "this is not a leaderboard record." Use direct negation only when needed for correctness or safety.
- A scientific manuscript is not a lab notebook, provenance report, or submission-office memo. Keep data-export mechanics, JSON/CSV-to-figure workflow, reference-search/BibTeX/Crossref workflow, bug-fix chronology, internal validation commentary, packaging instructions, and claims that readers should "trust" an artifact outside the manuscript. State only scientifically relevant methods, validation, results, and limitations.
- Do not address the target journal, editor, reviewer, or paper-building process inside the scientific narrative. Replace "the relevant question for this journal", "this paper therefore centers", rhetorical questions, and conversational verdicts such as "better for the wrong reason" with direct, evidence-led prose.
- Use `humanizer` selectively. Diagnose concrete patterns before editing; do not paraphrase correct technical passages merely to make them different. Preserve facts, equations, numbers, citations, terminology, and a formal journal register.
- When a target journal or submission portal exists, maintain one canonical metadata record. Synchronize title, author order, corresponding-author order and emails, affiliations, abstract, keywords, highlights, funding, data/code availability, and declaration status across TeX, PDF, title page, cover letter, source ZIP, standalone forms, and portal fields.
- Apply the strictest currently authoritative submission constraint. Hard limits in the live form/current journal instructions cannot be relaxed by a preference or older instruction; explicit user choices control optional content and routing within those limits. Count the exact plain-text field that will be pasted or uploaded; do not rely on an earlier count.
- Data availability, code availability, competing-interest, funding, and generative-AI statements are conditional submission elements. Add, remove, split, or keep them external according to the user's instruction and the target journal/form. Never imply that code is public when only the dataset is public, and never let standalone declarations contradict the manuscript or portal answers.
- Finalization requires source-to-output consistency: the compiled PDF, deliverable TeX, bibliography, figures, source archive, and nested package copies must all represent the same accepted revision. Recompile and rebuild stale archives after every metadata or prose change.
- Failed experiments are data; keep them and explain what they ruled out.
- Baselines come before proposed-method victory claims. A matched ANN control alone is not sufficient when recent strong domain or technique-family baselines exist.
- Guidance targets are binding. Do not mark an unmet required experiment or unmet strong expected result as "good enough"; complete it or pass a versioned replacement contract under `references/research-recovery.md` before writing.
- Do not treat P1A as permission to relax P5. P1A proves that the target has a credible experimental path; P5 still requires the approved strong result for the main claims, using real logged evidence.
- A binding target must be tied to a metric, comparator, uncertainty-aware evaluation plan, mechanism, and resource budget. It may be ambitious, but it cannot be a number chosen without prior evidence, baseline calibration, or an executable method path.
- P1B, P3A, and P5A are stop-loss gates, not decorative reports. Resolve their fatal concerns at the earliest applicable stage through the autonomous correction loop. Do not defer an early scientific or evidence concern to P9/P10 merely because implementation or drafting has already begun, and do not terminate the automation before screening feasible CCFA-generated repair routes.
- `ccf-paper-reviewer` must review the pre-draft evidence dossier scientifically at P5A and the actual manuscript in full mode at P9. `ccf-integrity-auditor` must distinguish planned evidence at P1B from real evidence at P3A, P5A, and P9; never promote a plan into a result.
- Never skip, reorder, or silently infer a pipeline stage. A correction is valid only as a recorded back-edge in `pipeline-state.md`, followed by re-execution of every affected downstream gate.
- Tables and figures must not drift far from their first textual explanation.
- Deliver the current compiled PDF and source artifacts required by the target venue. Apply explicit author length preferences and current journal limits; with neither, use evidence and completeness to determine appropriate length.
- The paper's numbered main sections must be exactly: `1 Introduction`, `2 Related Work`, `3 Method`, `4 Experiments and Results`, `5 Discussion`, `6 Conclusion`. Do not create alternative top-level structures.
- Do not put workflow logs, delivery notes, artifact checklists, citation-process narration, or "how I worked" text into the manuscript body. Keep those in external audit files.
- Do not add appendices, post-conclusion sections, reproducibility checklists, data-availability drafts, author checklists, or submission checklists to the paper just to satisfy page count. If such material is needed, integrate the scientific substance into the six required sections or store it as a separate audit/delivery artifact.
- Unless the user or target journal explicitly asks otherwise, the final paper content after `6 Conclusion` must be only acknowledgments/funding/data/code availability statements if appropriate, references, and required declarations. No research content should appear after the conclusion.
- Select a figure/table set that communicates the evidence clearly. No default count applies; each visual must have a scientific purpose.
- Preserve Figure 1 as the overall framework/architecture figure generated directly with GPT image generation and the existing reference-template style. Show only verified scientific components and labels allowed by `references/framework-figure-style.md`; do not use Nature skills for this overall figure. Use `nature-figure` for data visualizations unless unavailable and record any fallback.
- Use figures and tables where they materially help readers inspect evidence. Textual methods, setup, and interpretation subsections need not have their own visual, and the first paragraph need not open with a citation.
- Citation verification must include duplicate-paper detection, not only existence and bibliographic correctness. Treat matching DOI, arXiv id, normalized title, or conference/preprint versions of the same work as potential duplicates until resolved in `reference-dedup-audit.md`.
- The final paper must be delivered as TeX source and a compiled PDF. Fix compilation errors before delivery.
- Do not submit, commit, push, or otherwise publish changed files without explicit user instruction.
- Do not finalize the paper until guidance-file coverage and figure/table insertion audits are complete.
